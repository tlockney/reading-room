The AI/ML Learning Path

A self-directed path to hands-on AI/ML competency—able to build, evaluate, and make architecture calls, not a researcher. Six phases, artifact-based progression, no calendar. This is the reading copy; the working notes—progress, glossary, per-unit notes—live in the Obsidian vault.

§ 01Design principles

This is a long-deferred dive, finally taken, and preparation for the next years of technology and product leadership wherever that happens. Metron provides useful grounding and real data along the way, but the capability being built is portable: it should serve the current role, the advisory practice, and whatever comes after equally well. Four principles shape everything below.

  1. Top-down, build-first. Use a thing, then peel back layers to understand it. Every phase produces a working artifact before it explains the math underneath.
  2. Just-in-time math. No prerequisite courses. Each phase has a math sidebar naming the 2–4 concepts it actually needs, with a targeted resource. Reactivation, not instruction from zero.
  3. One thread, small closed loops. One active phase at a time. Each unit fits a 60–90 minute session and ends with something runnable or a note written. Writing the note is the comprehension check.
  4. No calendar. Progression is artifact-based. You're "at" whatever the last committed artifact says. Gaps cost nothing.

§ 03Working the path

The session ritual

  1. Open the Progress note in Obsidian.
  2. Find the next unchecked unit. Open its phase note.
  3. Do the unit. Stop when the artifact exists—resist continuing.
  4. Write or update the unit's note (a few sentences in your own words is enough).
  5. Check the box. Done.

Re-entry after a gap

Don't re-read everything. Open the Progress note, skim your own note for the last completed unit (not the source material), do the next unit. If the last unit's note doesn't make sense to you anymore, redo that unit—that's signal, not failure.

Standing resources

  • 3Blue1Brown—linear algebra, calculus, and neural net intuition. The math sidebar workhorse.
  • StatQuest—stats concepts, short and unpretentious.
  • Andrej Karpathy's videos—the Phase 3 backbone; his LLM intro appears in Phase 0.
  • Simon Willison's blog—running commentary on the LLM ecosystem from an engineer's perspective.
Glossary

Maintain the AI-ML Glossary note in Obsidian as you go. Add a term the moment you look one up; a one-line definition in your own words beats a pasted one. Mark guesses with (?) and fix them when the relevant phase teaches you better—the (?) marks become a nice progress signal.

§ 04Phase 0 — Orientation Map

Goal: a single mental-model note that maps the field, which you'll annotate for the rest of the path. Size: 1–2 sessions. Stack: notes only.

0.1 — The map

Watch, then write. Two inputs:

  • Karpathy, Intro to Large Language Models (1 hr)—what an LLM physically is, training vs. inference, why it's "just" a big file of numbers plus a small amount of code.
  • 3Blue1Brown, But what is a neural network? (20 min)—a preview, not mastery. You'll return to this material properly in Phase 3.

Artifact: a note titled How ML Actually Works - My Map covering, in your own words: the taxonomy (classical ML vs. deep learning vs. generative/LLM, and what kinds of problems each owns); training vs. inference and why they have wildly different cost profiles; what "a model" physically is—an architecture (code) plus weights (a file of numbers), and where the knowledge lives; and a hand-drawn or Excalidraw diagram of the taxonomy. Drawing it forces the choices that reading lets you skip.

Expect wrong or fuzzy entries. The point of the map is having something concrete to correct later—each phase should send you back here to annotate.

0.2 — The glossary seed

Create the glossary and seed it with one-line definitions, your own words, for: model, weights/parameters, training, inference, loss, gradient, embedding, token, context window, fine-tuning, hyperparameter, overfitting. Some definitions will be guesses—mark those with (?).

Artifact: the glossary note, all twelve terms present.

Math sidebar

None. That's deliberate—Phase 0 is orientation, and adding math here front-loads exactly the kind of prerequisite work this path avoids.

Exit criterion

You can explain to a smart engineer, without notes: where LLMs sit in the ML taxonomy, and the difference between training and inference—including why inference is what you pay for per-request and training is what cost someone $100M.

§ 05Phase 1 — Use Models Seriously

Goal: working fluency with model APIs, embeddings, and retrieval—the material most directly relevant to product and architecture decisions. Ends with a RAG CLI over your own Readwise highlights. Size: 6 units. Stack: TypeScript/Deno, Anthropic API (or Bedrock—see 1.1), SQLite + sqlite-vec.

This is home turf: API-shaped work in your preferred stack. The unfamiliar part is what's inside the calls, and that's the point.

1.1 — First structured call

A Deno CLI script that calls the Messages API and validates the response into a typed structure (Zod or plain type guards). Play with: system vs. user prompts, temperature, max tokens. Break it on purpose—malformed outputs, truncation—and handle it. Bedrock vs. direct Anthropic API: pick one and stop thinking about it. Direct API has less ceremony; Bedrock exercises your AWS muscles and matches what Metron would likely deploy. Artifact: ask.ts.

1.2 — Tool use

Define 2–3 tools (current weather, filesystem search, a calculator), pass the schemas, run the loop: model requests tool → you execute → return result → model continues. This is the primitive under every "agent" product; seeing the loop demystifies the category. Artifact: agent.ts, with visible tracing of each round trip.

1.3 — Embeddings by hand

Generate embeddings for ~20 short texts (Voyage AI or Bedrock Titan—same rule as 1.1: pick one and stop thinking about it). Write cosine similarity yourself in TypeScript—it's ten lines—and build a tiny "find the most similar sentence" demo. Then poke at the failure modes: negation, sarcasm, near-duplicates. Artifact: similarity.ts plus a note on what embeddings capture and what they miss.

Caveat · one model

Whichever embedding model you pick, write it down: the index you build in 1.4 and every query in 1.5 must use the same model (and version). Mixing them is the classic first RAG bug—everything runs, nothing retrieves well. Background: Embeddings & Retrieval.

Math sidebar (before or during this unit): vectors, dot products, cosine similarity—3Blue1Brown, Essence of Linear Algebra, chapters 1–3 and 9. One idea to hold onto: "similarity = angle between arrows in a very high-dimensional space." Everything in units 1.4–1.5 leans on it.

1.4 — Chunk and index the corpus

Pull highlights from your readwise-sqlite database. Chunk them (highlights are conveniently pre-chunked—note why that matters, and what you'd do with long documents instead). Embed and store in SQLite with sqlite-vec. Artifact: index.ts plus a populated vector table, with a count-and-spot-check step so you trust the index.

1.5 — Retrieval + generation

The full RAG loop: embed the query, retrieve top-k, stuff into the prompt with instructions to ground answers in the provided passages and cite them. Compare answers with retrieval on vs. off. Try adversarial questions the corpus can't answer—does it admit that or confabulate? Artifact: ask-my-highlights.ts—the working RAG CLI. This one you'll actually keep using.

1.6 — Evaluate it

Write 10–15 question/expected-answer pairs against your corpus. Score the pipeline: retrieval hit rate (did the right passage surface?) separately from answer quality (LLM-as-judge, or your own rubric). Change one thing—top-k, chunking, prompt—and measure the effect. This unit is deliberately small. It plants the flag for Phase 4: the eval set is the product spec. Artifact: eval.ts plus a short results note.

Caveat · small-n noise

With 15 questions, a one-answer swing is noise, not signal. The "is the difference real?" section of Statistics for Engineers is the ten-minute read that keeps this unit honest.

Stretch (optional, explicitly not required)

Hybrid search (keyword + vector), reranking, streaming responses. Parked here so they don't become scope creep inside the units above.

Exit criteria

  • The RAG CLI works against your real highlights and you use it at least once for a real question.
  • You can explain to a smart engineer: what an embedding is, why RAG exists (vs. fine-tuning, vs. long context), and the main knobs that change RAG quality.
  • Your Phase 0 map has at least two annotations correcting or sharpening earlier entries.

§ 06Phase 2 — Classical ML Fundamentals (skeleton)

Goal: working knowledge of the pre-deep-learning toolkit—regression, classification, trees/ensembles, clustering—and the discipline around it (train/test splits, validation, overfitting). This is where Python enters. Time-series anomaly detection and forecasting anchor the applied units—territory that's broadly valuable across domains and that happens to map directly onto Metron's sensor data if you choose to use it. Size: ~6–7 units, detailed near the end of Phase 1. Stack: Python (uv), Jupyter or marimo notebooks, pandas, scikit-learn.

Planned units

  1. Python-for-polyglots setup—uv, notebooks, pandas idioms. Short; you know how programming works. The Python Environment for Polyglots guide carries the detail.
  2. Linear regression on a real dataset—fit, residuals, what the coefficients mean.
  3. Classification—logistic regression, precision/recall/confusion matrices.
  4. Trees and ensembles—decision trees, random forests, gradient boosting; why tabular data still belongs to them.
  5. Clustering and anomaly detection—k-means, isolation forests; applied to time-series—a public energy/water/traffic dataset, homelab sensor data from Home Assistant, or Metron flow data; pick whichever is richest and easiest to get.
  6. The discipline unit—overfitting, bias-variance, cross-validation, leakage. The unit that makes you dangerous in a review meeting.

Math sidebar (planned)

Distributions, mean/variance/standard deviation, correlation, sampling. Statistics for Engineers is the backbone here, with StatQuest for anything that needs a second angle—this is the phase that quietly delivers most of the missing statistics background.

Likely resources

  • Géron, Hands-On Machine Learning (3rd ed.)—chapters 1–7 roughly cover this phase.
  • Classical ML Vocabulary—the reference for every term this phase introduces.
  • StatQuest playlists on regression, classification metrics, and bias-variance.

Exit criterion (draft)

Given a tabular dataset and a question, you can pick a sensible model family, fit it, validate it honestly, and explain why the honest number is lower than the naive one.

§ 07Phase 3 — Neural Nets from Scratch (skeleton)

Goal: convert "I use models" into "I understand what's happening." Build a tiny neural network and its training loop from scratch, then meet PyTorch as a labor-saving device rather than a black box. This is where the calculus reactivation happens. Size: ~5–6 units, detailed near the end of Phase 2. Stack: Python, then PyTorch.

Planned units

  1. Karpathy's micrograd—build backprop by hand on scalar values. The single highest-leverage video in the field.
  2. A tiny network on a toy problem, trained with your own gradient descent loop.
  3. First makemore sessions—bigram model, then a simple neural language model. Watching a language model emerge from first principles.
  4. Port to PyTorch—same model, framework does the gradients. Note exactly what the framework saved you.
  5. Training-run literacy—loss curves, learning rates, what "it's not converging" looks like.

Math sidebar (planned)

Derivatives, chain rule, gradient descent. 3Blue1Brown's Essence of Calculus (selected chapters) plus his neural-network backprop videos. Your rusted math inclination gets its real workout here—budget for it and don't rush the sidebar.

Exit criterion (draft)

You can explain backprop with a pencil—small example, actual numbers—and read a PyTorch training loop knowing what every line is for.

§ 08Phase 4 — LLM Internals and Evaluation (skeleton)

Goal: intuition-level understanding of how LLMs work (tokenization, attention, sampling) and—most important for the role—real competence in evaluation: how to know whether an AI feature works, and how to decide between prompting, RAG, and fine-tuning. Size: ~5–6 units, detailed near the end of Phase 3. Stack: mixed—Python for internals, TypeScript for the eval harness (it should feel like production code).

Planned units

  1. Tokenization—BPE, why token counts surprise people, cost implications.
  2. Attention at intuition level—3Blue1Brown's transformer videos. Understanding the picture, not implementing the paper.
  3. Inference mechanics and economics—prefill vs. decode, the KV-cache, quantization, why long context and prompt caching cost what they do. Verifies LLM Discourse Primer §5–6 against real understanding.
  4. Sampling—temperature, top-p, why the same prompt gives different answers; softmax and log-probabilities.
  5. The post-training landscape—SFT, preference optimization, reasoning-model training; what each does to behavior. Verifies primer §3.
  6. The decision framework—prompting vs. RAG vs. fine-tuning: costs, failure modes, when each wins. Written as a one-page decision note you could hand a PM.
  7. Evals in depth—build a real eval harness in TypeScript; graded rubrics, LLM-as-judge and its pitfalls, regression testing prompts like code. Extends unit 1.6's seed; the Evals primer is the reference.
  8. Stretch: Karpathy's build-GPT-from-scratch, if Phase 3 left appetite for it.

A standing task for this phase: sweep the Discourse Primer and the glossary, correcting anything the units proved wrong or shallow.

Math sidebar (planned)

Probability basics, conditional probability, softmax, log-likelihood, sampling. Statistics for Engineers + 3Blue1Brown.

Exit criterion (draft)

Given a proposed LLM feature, you can specify its eval set before its implementation, and defend a prompting/RAG/fine-tuning recommendation with cost and failure-mode reasoning.

§ 09Phase 5 — Production Judgment (skeleton)

Goal: cash the path out into leadership judgment—the kind that transfers across roles. Cost modeling, latency, observability, security, failure modes, evaluating vendor claims, and—critically—when not to use ML at all. Capstone: an architecture memo for a real decision actually in front of you. Size: ~4–5 units, detailed near the end of Phase 4. Stack: memo-writing and architecture review; small spikes only where a number needs verifying.

Planned units

  1. Cost and latency modeling—tokens as the unit of cost; caching, batching, model-size tiering; a real spreadsheet for a hypothetical feature at Metron's scale.
  2. Failure modes and safety—hallucination in product contexts, prompt injection, data boundaries; what "the model is wrong X% of the time" means for UX design.
  3. Observability and lifecycle—logging, drift, versioning prompts and models, feedback loops.
  4. The "should this even be ML?" unit—heuristics vs. classical ML vs. LLMs vs. plain code; build vs. buy; reading vendor claims with the internals knowledge from Phases 3–4. The honest decision tree.
  5. Capstone: an architecture memo for a real audience and a real decision—a Metron feature, an advisory client, or a side project you'd actually build. Problem, approach, eval plan, cost model, risks. The memo is the proof the path worked, and the template is reusable for every such decision afterward.

Math sidebar

None new—this phase applies what the others built.

Exit criterion (draft)

The memo exists, and you'd be comfortable defending it in a real architecture review.
