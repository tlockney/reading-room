Bottom line up front

Hindsight (vectorize-io/hindsight, ~21k stars, MIT) is the current state-of-the-art open-source agent memory system: retain / recall / reflect, a four-strategy retrieval engine, and automatic consolidation of raw facts into durable observations. It is #1 on the BEAM memory benchmark and ships with an MCP server, SDKs in four languages, and 52 official integrations.

The engine is the constant; the integration is the variable. Hermes gets a mature native memory provider (auto-recall + auto-retain hooks, three explicit tools). Claude Code, DeepSeek Harness and nine other CLI agents are covered by one shared "coding agents" package with per-repo banks built from git history and conversations. Pi gets an independent, opinionated extension (epimetheus). Plain Claude (the desktop app) has no first-party plugin — you wire the MCP server yourself. This dossier walks the system, then the setup for each of the five, then the use cases and the operational gotchas that actually bite.

01

The memory model

Hindsight is built around a simple thesis: agents don't need a transcript-replay system, they need a belief store that consolidates. Information goes in via retain(), comes out via recall() (raw matches) or reflect() (reasoned synthesis), all scoped to an isolated memory bank.

Memory hierarchy

// Four memory typesbottom = raw, top = curated
TypeStoresExample
Mental ModelUser-curated, cached reflection for common queries"Team communication best practices"
ObservationConsolidated, deduplicated beliefs with evidence"User was a React dev, has since switched to Vue"
World FactObjective facts received from the user"Alice works at Google"
Experience FactThe bank's own actions and interactions"I recommended Python to Bob"

During reflect, Hindsight checks sources in priority order: Mental Models → Observations → Raw Facts. Mental models are the cheapest, most-curated layer; raw facts the ground truth to fall back on.

Multi-strategy retrieval (TEMPR)

Every recall runs four search strategies in parallel, then fuses the results:

  • Semantic — conceptual similarity and paraphrasing (embedding search).
  • Keyword (BM25) — names, technical terms, exact identifiers.
  • Graph — related entities and indirect connections across the entity graph.
  • Temporal — time-anchored queries ("last spring", "in June", "before the migration").

That temporal + graph layer is what distinguishes Hindsight from plain RAG: it can answer "what did Alice do last spring?" even when no stored chunk contains that exact phrasing.

Observation consolidation

After retention, Hindsight automatically consolidates related facts into observations:

  • Deduplication — overlapping facts merge into one durable observation instead of piling up as repeats.
  • Evidence tracking — each observation references the source memories that support it (with exact quotes) plus a proof count.
  • Continuous refinement — observations are updated, not overwritten, when new evidence supports, contradicts or extends them; history is preserved.
  • Freshness awareness — if newer memories haven't been consolidated yet, reflect treats affected observations as stale and re-verifies them against raw facts.

Mission, directives & disposition

Banks can be configured to shape how the agent reasons during reflect (these settings do not affect recall):

  • Mission — natural-language identity for the bank ("I am a research assistant specializing in ML; I prefer simplicity over cutting-edge").
  • Directives — hard guardrails that must never be violated ("never recommend specific stocks", "always cite sources").
  • Disposition — soft reasoning traits on a 1–5 scale (skepticism, literalism, empathy).
What this buys you · BEAM The underlying model reportedly uses a ~20B open backbone that outperforms full-context GPT-4o on the same long-term-memory benchmark. The paper is "Hindsight is 20/20: Building Agent Memory that Retains, Recalls, and Reflects" (arXiv 2512.12818).

Clients & interfaces

  • REST API — full CRUD over /v1/default/banks/{bank_id}/…: /memories, /memories/recall, /reflect, /documents, /mental-models, /operations, /export, /consolidate.
  • MCP server — http://localhost:8888/mcp/{bank_id}/ (single-bank) or /mcp/ (multi-bank, 29 tools). This is how Claude and Claude Desktop connect.
  • SDKs — Python (hindsight_client), TypeScript, Go, plus the CLI.
  • CLI — two binaries with different jobs. hindsight is the API client: bank, memory (list/get/recall/reflect/retain/clear), document, entity, tag, chunk, operation, mental-model, directive, webhook, audit, health, metrics, plus explore — a k9s-style TUI for walking banks, memories and entities and firing recall/reflect interactively. hindsight-embed is the lifecycle tool: profile, daemon, bank and UI management. (Verified against hindsight 0.8.6.)
  • Web UI — hindsight-embed -p <profile> ui start serves a Next.js "control plane" on daemon_port + 10000 for browsing memories, observations, entities and operations. It is a thin client over the dataplane: it connects out to the daemon's REST port and, with no API key set, runs open — and it binds 0.0.0.0, not localhost. On a laptop that shares a coffee-shop LAN, that is your whole memory bank on an unauthenticated port.

The hindsight CLI resolves its target in a fixed order, and it is worth knowing before you debug a "wrong bank" mystery: HINDSIGHT_API_URL / HINDSIGHT_API_KEY in the environment win, then a named profile from ~/.hindsight/cli-profiles/<name>.toml (selected with -p or HINDSIGHT_PROFILE), then the default http://localhost:8888. Note the near-collision: CLI profiles live in ~/.hindsight/cli-profiles/, while daemon profiles live in ~/.hindsight/profiles/. Same word, different directory, different job — and a daemon profile does not give the CLI a URL. If you start a daemon on :9177 and then run bare hindsight memory list, it will talk to :8888 and report nothing.

Local embedded — the daemon you probably run

The local-embedded path (what Hermes uses here) is a small daemon with an embedded PostgreSQL (pg0), started on demand and shut down after an idle timeout (default 300s; HINDSIGHT_EMBED_DAEMON_IDLE_TIMEOUT=0 keeps it resident). It needs its own LLM for fact extraction — configured independently of the host agent's model. On this machine that's deepseek-v4-flash via Ollama Cloud (https://ollama.com/v1).

Config gotcha · three sources of truth The Hermes plugin reads ~/.hermes/hindsight/config.json; the daemon reads ~/.hindsight/profiles/hermes.env; and daemon start re-syncs the env file from config.json. Change the extraction model in BOTH or the daemon silently reverts it on next start. The third file, ~/.hermes/config.yaml under memory:, decides whether Hermes consults the provider at all — and it is the one people forget, because it looks like unrelated agent config.
Port collision · PG-1 The pg0-managed instance takes port 5432 — the Postgres default — with the credentials hindsight/hindsight and database hindsight (Postgres 18.1 here). If you also run a local Postgres for development, one of the two loses. The daemon log shows the symptom as a bare port 5432 failed: Connection refused during startup, which reads like a Hindsight bug and is not one.

Five integrations, face-off

The five tools you asked about connect to Hindsight in five different ways — native provider, MCP + hooks, shared plugin, independent extension, and a Cordis plugin. The table is the whole argument of this dossier.

// Integration mechanismsper tool
ToolMechanismAuto recall/retainExplicit toolsScope
HermesNative memory provider (hermes memory setup)Yes — pre_llm_call / post_llm_call hookshindsight_retain/recall/reflectOne bank (hermes), global
Claude (desktop app)MCP server only (hindsight-local-mcp)No hooks — manual tools only29 MCP tools (retain, recall, reflect, pages…)Per-bank via /mcp/{bank}/
Claude CodeCoding-agents plugin (hooks + MCP + skill)Yes — SessionStart / UserPromptSubmit / Stop hookshindsight_* MCP toolsPer-repo: coding-agent::{gitProject}
Piepimetheus extension (ambient + queue)Yes — injected per user prompthindsight_retain/recall/reflect + commandsProject/user/session-scoped via tags
DeepSeek Harness (dsh)Cordis plugin via coding-agents packageYes — native plugin tools, no MCPhindsight_* toolsPer-repo, resolved per session workspace

Three structural notes worth internalizing:

  • Claude Code, Codex, opencode, Kilo, Cursor, Copilot, Grok, Antigravity, Devin, Cline and DeepSeek Harness share one package (@vectorize-io/hindsight-coding-agents). Banks are per-repo and harness-neutral by default, so every agent working in a repo reads and writes the same memory.
  • Plain Claude is the outlier. No first-party plugin exists; you get memory only where you wire the MCP server in, and there are no automatic recall/retain hooks — the agent must call the tools itself. (The Claude Agent SDK path adds hooks, but only for agents you write with the SDK.)
  • Pi's epimetheus is independent and deliberately conservative. It follows Hindsight's documented best practices closely, queues retains to disk, and fixes a known Hermes gap (Hermes recall is one turn behind — issue #5820). It's beta and needs its own Hindsight server.

Setup per tool

Everything below is verified against the current docs (2026-08). Where a path is deprecated or superseded, it's flagged.

4.1 Hermes — native provider

Hermes ships Hindsight as a built-in memory provider. The old standalone hindsight-hermes plugin is deprecated; use the native provider.

# Wizard — picks cloud or local-embedded and writes ~/.hermes/hindsight/config.json
hermes memory setup          # select "hindsight"

# Manual (cloud):
hermes config set memory.provider hindsight
echo "HINDSIGHT_API_KEY=your-key" >> ~/.hermes/.env
echo "HINDSIGHT_API_URL=https://api.hindsight.vectorize.io" >> ~/.hermes/.env

# Verify
hermes memory status

Where the settings actually live

Two files, not one, and they answer different questions. ~/.hermes/config.yaml decides whether and how hard Hermes uses memory at all; ~/.hermes/hindsight/config.json decides which Hindsight it talks to. Neither file mentions the other, which is why "I configured Hindsight and nothing happened" is usually a config.yaml problem.

# ~/.hermes/config.yaml — the agent-side policy
memory:
  memory_enabled: true        # master switch for the memory subsystem
  user_profile_enabled: true  # maintain USER.md alongside MEMORY.md
  write_approval: false       # false = retain without prompting the user
  memory_char_limit: 4000     # cap on injected memory context
  user_char_limit: 2000       # cap on injected user-profile context
  provider: hindsight         # which external provider is active (one at a time)
  nudge_interval: 10          # turns between "consider saving this" nudges
  flush_min_turns: 6          # minimum turns before a retain flush fires

// ~/.hermes/hindsight/config.json — what `hermes memory setup` writes.
// Note the snake_case: this is not the camelCase schema the coding-agents
// package uses, and settings do not carry across.
{
  "mode": "local_embedded",           // "local_embedded" | "cloud" | "self_hosted"
  "apiKey": "",                       // cloud/self-hosted only
  "timeout": 120,                     // seconds, per API call
  "idle_timeout": 0,                  // 0 = daemon stays resident
  "retain_tags": "",                  // tags stamped on every retained memory
  "observation_scopes": "",           // consolidation scoping ("" = bank default)
  "retain_source": "",
  "retain_user_prefix": "User",       // speaker labels in the retained transcript
  "retain_assistant_prefix": "Assistant",
  "banks": {
    "hermes": { "bankId": "hermes", "budget": "mid", "enabled": true }
  },
  "llm_provider": "openai_compatible", // extraction LLM — independent of the agent's model
  "llm_base_url": "https://ollama.com/v1",
  "llm_model": "deepseek-v4-flash",
  "bank_id": "hermes",                 // active bank
  "recall_budget": "mid"               // low | mid | high — size of injected recall
}

The knobs that matter in daily use: recall_budget (and the per-bank budget) trade injected-context size against prompt cost; retain_tags is how you keep work and personal memories separable inside one bank; observation_scopes controls whether consolidation builds one belief set or several; and idle_timeout: 0 is what stops the daemon shutting down between turns and paying the cold-start cost again. A handful of these are also env-overridable from ~/.hermes/.env — HINDSIGHT_LLM_API_KEY, HINDSIGHT_TIMEOUT, HINDSIGHT_IDLE_TIMEOUT.

Two details in there are easy to miss. First, the provider name is translated on the way down: config.json says llm_provider: openai_compatible, but the env file the daemon actually reads says HINDSIGHT_API_LLM_PROVIDER=openai. They mean the same thing; a grep for the wrong one finds nothing. Second, the daemon log at ~/.hindsight/profiles/hermes.log is 103 MB at info level and nothing rotates it. Set HINDSIGHT_API_LOG_LEVEL=warning once the install is stable, or add it to your own log rotation.

Live finding · HERM-2 hermes memory status on this machine reports Plugin: installed ✓ but Status: not available ✗, with ✗ HINDSIGHT_API_KEY listed as missing — despite mode: local_embedded, where a key is by definition not needed. The readiness check appears to test for the cloud credential unconditionally. Treat a red memory status as inconclusive in local-embedded mode and verify the real thing instead: start the daemon and hit its REST port, or run hindsight -p hermes bank stats against :9177.
Gateway gotcha · HERM-3 hermes memory status also warns that systemd and gateway services do not inherit ~/.hermes/.env. This matters precisely for the cross-platform assistant use case in §05: the Telegram/Discord/Slack gateways are where you most want memory, and they are the surface most likely to start without the Hindsight variables set. Put them in the service environment, not just the dotenv.

Built-in memory does not go away

The advice you will find in most write-ups — run hermes tools disable memory if the model keeps preferring Hermes's markdown memory over Hindsight — reaches for the wrong lever. The CLI says so plainly: "Built-in memory (MEMORY.md/USER.md) is always active." Only one external provider can be active at a time, and the built-in layer runs underneath whichever one you pick. What the commands actually do:

  • hermes memory off — disables the external provider, leaving built-in memory running.
  • hermes memory reset — erases MEMORY.md and USER.md. This is the only way to clear built-in memory, and it does not touch Hindsight.
  • hermes tools disable memory — disables the memory toolset, i.e. the model's explicit memory tools. Automatic injection still happens, so this narrows the surface rather than resolving a conflict.
  • config.yaml → memory.memory_enabled: false — the actual master switch.

So the two layers coexist by design, and on this machine both are live. That is usually fine: built-in memory is a short curated file the user edits, Hindsight is the large consolidated store. It becomes a problem only when the same fact lives in both and they disagree — at which point the built-in file wins, because it is injected verbatim rather than retrieved.

Known gap · HERM-1 Auto-recall in Hermes runs one turn behind the current prompt (NousResearch/hermes-agent#5820) — the memory injected reflects the previous message. Epimetheus and the coding-agents package both avoid this by building the query from the incoming prompt. The diagram below shows why the hook's position in the turn is what causes it.

4.2 Claude (desktop app / Claude.ai)

No plugin — run the local MCP server and point Claude Desktop at it. This is the official path for "Claude long-term memory across conversations."

# 1. Start the local MCP server (embeds Postgres, exposes /mcp/)
HINDSIGHT_API_LLM_API_KEY=sk-... uvx --from hindsight-api hindsight-local-mcp
# or with Ollama (no key):
HINDSIGHT_API_LLM_PROVIDER=ollama HINDSIGHT_API_LLM_MODEL=llama3.2 uvx --from hindsight-api hindsight-local-mcp

// 2. ~/Library/Application Support/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "hindsight": {
      "type": "http",
      "url": "http://localhost:8888/mcp/hermes/"   // single-bank mode
    }
  }
}

Multi-bank mode uses http://localhost:8888/mcp/ and selects the bank per call via the bank_id parameter or X-Bank-Id header. First startup downloads the embedding model (~100MB) and initializes the DB. Data persists in ~/.pg0/hindsight-mcp/.

For agents you write, the Claude Agent SDK integration adds hooks so recall/retain happen automatically:

pip install hindsight-claude-agent-sdk

from claude_agent_sdk import query, ClaudeAgentOptions
from hindsight_claude_agent_sdk import create_hindsight_server

server = create_hindsight_server(bank_id="my-agent",
                                 hindsight_api_url="http://localhost:8888")
# pass server via ClaudeAgentOptions(mcp_servers={"hindsight": server})
Scope caveat · CLAUDE-1 The MCP route gives the agent 29 explicit tools (retain/recall/reflect, mental models, directives, knowledge pages, documents) but no automatic injection — memory only appears when the model chooses to call a tool. Fine for a research assistant; weaker as a fire-and-forget memory layer.

4.3 Claude Code — coding-agents plugin (current)

The recommended path is the shared coding-agents package; the older per-agent plugin is superseded. One command wires three hooks into ~/.claude/settings.json, MCP via claude mcp add, and a companion skill.

cd /path/to/your/repo
npx @vectorize-io/hindsight-coding-agents install claude-code
# optional flags:
#   --server cloud|self-hosted|daemon   where memory lives
#   --api-url http://localhost:8888     for an existing server
#   --import-conversations              re-ingest past local transcripts
npx @vectorize-io/hindsight-coding-agents uninstall claude-code   # removes exactly what install added

Behavior (hooks): SessionStart health check + cold-repo seed, UserPromptSubmit auto-recall injected as additionalContext (invisible to chat, visible to Claude), Stop auto-retain (async). Explicit hindsight_* MCP tools plus a knowledge-page skill teach the agent how its own memory works.

Config lives in ~/.hindsight/coding-agent.json (shared by all agents) — note that this is a separate config tree from the Hermes wiring in §4.1, in camelCase rather than snake_case, and nothing carries across. On this machine that file does not exist: Claude Code is not currently wired to Hindsight, so the Hermes bank and any future per-repo coding banks would start out with no shared history. Key settings:

{
  "apiUrl": "http://127.0.0.1:9077",      // local daemon; cloud default otherwise
  "bankIdTemplate": "coding-agent::{gitProject}",  // harness-neutral per-repo bank
  "autoSeed": true,                        // seed cold repo from git history
  "seedLimit": 300,                        // most-recent-N commits
  "gitIngest": "message",                  // "message" | "full" (diffs) | "none"
  "optInOnly": false,                      // true = memory only in optInPaths
  "optInPaths": ["~/work/client-x"],
  "retainTags": ["project:{gitProject}", "env:work"],
  "observationScopes": "shared"            // one belief set per bank (all agents)
}

Local-daemon mode starts hindsight-embed on demand at 127.0.0.1:9077 (one daemon serves every agent; an existing server is adopted, never restarted). It needs an LLM key for extraction — first of OPENAI_API_KEY, ANTHROPIC_API_KEY, GEMINI_API_KEY, GROQ_API_KEY — or falls back to the Claude Code CLI (no key).

macOS · DSH-MAC-1 On macOS the local daemon compiles litellm from source (no macOS wheels) — you need a current Rust toolchain from rustup.rs or daemon startup fails.

4.4 Pi — epimetheus extension

Pi is the open-source coding agent by can1357; its official Hindsight integration is epimetheus (noctuid) — a beta, GPL-3.0 extension with an unusually careful design. It needs its own Hindsight server; it won't ride on the Hermes daemon profile.

# 1. Server (own profile/port)
uvx hindsight-embed@latest profile create pi --port 9100
uvx hindsight-embed -p pi configure            # LLM provider/key
uvx hindsight-embed@latest -p pi bank create default
# keep daemon resident (required by the extension):
echo "HINDSIGHT_EMBED_DAEMON_IDLE_TIMEOUT=0" >> ~/.hindsight/profiles/pi.env

# 2. Install the extension (pin a tag — config API is in flux)
pi install @noctuid/epimetheus@<latest-tag>

// 3. ~/.pi/agent/epimetheus/config.jsonc
{
  "apiUrl": "http://127.0.0.1:9100",
  "apiKey": "your-api-key",
  "bankId": "default",
  "constantTags": ["harness:pi", "user:me"],
  "toolsEnabled": ["retain", "reflect"],
  "autoRecallPersist": true,
  "autoRecallDisplay": true,
  "observationScopes": [["user:me"], ["{project}"]],
  "autoRecallTags": ["user:me"],
  "maxRecallTokens": 2048
}

Highlights: automatic retention on session lifecycle (switch/fork/reload/compact/quit), disk-backed queue that survives Hindsight being down, past-session ingestion of any historical session, project/user/session scoping via tags, and reflect-backed mental-model workflows. The author hand-verifies queue and parsed-session files — a level of correctness focus most memory integrations don't have.

Beta maturity · PI-1 Beta software; the author recommends locking to a specific tag and reviewing the changelog before updates. Re-read the best-practices section early — changing the retain/observation mission later means re-ingesting old sessions.

4.5 DeepSeek Harness (dsh)

DeepSeek's plugin-first coding agent ("everything is a plugin," built on the Cordis framework) gained Hindsight memory via the same coding-agents package. One command, no MCP:

npx @vectorize-io/hindsight-coding-agents install dsh
# alternative package route:
dsh plugin --profile web add @vectorize-io/hindsight-coding-agents

The installer adds a Cordis plugin row to $DSH_HOME/cordis.patch.yml (~/.dsh by default), which every dsh profile composes. Two dsh-specific notes: because one dsh process serves several repositories (the Web UI opens sessions in whatever directory you pick), the bank is resolved per session workspace, not per process; and dsh has no plugin-facing notice channel, so the seed line goes to the plugin log rather than the UI. Everything model-facing — recalled memory, the knowledge preamble, the hindsight_* tools — is unaffected.

Session transcripts live as Zstandard-framed JSONL under $DSH_HOME/sessions; importing past sessions needs Node 22.15+ (the import is skipped with a reason on older Node rather than silently importing nothing). Same per-repo banks as Claude Code — both agents share coding-agent::{gitProject}.

05

Common use cases

Per-repo coding memory (the flagship)

The coding-agents package is zero-setup: a repo's git history and conversations flow into its bank in the background. The stated premise — most of a real fix is derivable from the code, but the last mile hinges on project-specific decisions (a rounding rule, a retry allowlist, a tie-break policy) that live only in git history and past chats — is exactly the gap memory fills. Cold repos are auto-seeded from the last N commits, with an optional headless codebase survey run under the harness's own CLI.

Cross-agent shared memory

Because the default bank template (coding-agent::{gitProject}) is harness-neutral, Claude Code, Codex, opencode and dsh all read and write one bank per repo. A decision recorded by one agent is recalled by every other. Use observationScopes: "shared" so consolidation builds one set of beliefs per bank instead of parallel per-agent belief sets.

Subagents with their own brains

Claude Code's plugin exposes a create-agent skill that scaffolds a subagent file under ~/.claude/agents/ with an isolated bank; dynamic bank IDs (dynamicBankId, granularity agent/channel/user) isolate memory per agent, channel, or user — including Claude Code Channels (Telegram/Discord/Slack).

Personal-assistant memory across platforms

Hermes in gateway mode (Telegram/Discord/Slack) creates a fresh agent per message; the pre_llm_call hook recalls relevant memories every turn regardless of platform, so the assistant remembers who you are, your preferences, and open threads across surfaces.

Knowledge pages — living project docs

Newer feature: banks can maintain knowledge pages (architecture, conventions, in-flight initiatives) as living documents over the bank's memories, auto-refreshed after each consolidation (or on a cron, or manually). Future sessions start from them.

Retroactive memory via past-session ingestion

Both the coding-agents package (--import-conversations) and epimetheus can ingest any past session — not just ones that had the plugin loaded. Ingestion is idempotent (dedup by document id) and respects session attribution so forks don't duplicate parent content.

Mental models & guardrails

Mental models cache reflect answers for common queries ("What are the user's dev preferences?") and can auto-refresh when new observations land. Directives provide hard guardrails that reflect will not violate — useful for compliance-flavored assistants.

Bulk knowledge loading

For vaults/docs, load through the REST API rather than per-item tool calls: batch 5 items per request, always async: true, cap content at ~30KB per item, tag the source filename in context, and filter aggressively (skip daily notes and third-party exports — noise beats signal). Verify the extraction model before a big load; a dead model accepts everything into the queue then fails every extraction.

06

Verdict & risk

Where it wins

  • The engine is genuinely state-of-the-art — temporal + graph retrieval, evidence-grounded consolidation, BEAM #1. If you're choosing a memory system, Hindsight is the default recommendation.
  • One shared integration for a dozen coding agents, with per-repo banks that let every agent contribute to one memory. This is the strongest "write once, remember everywhere" story in the space.
  • Local-first options are real — a personal daemon with embedded Postgres needs no external account, and the MCP server is trivial to stand up for any MCP client.

Where it bites

  • Integration quality varies more than engine quality. Hermes has the one-turn-behind recall gap (#5820); plain Claude gets no automatic hooks at all; Pi's epimetheus is excellent but beta and self-hosted.
  • The plugin landscape is mid-migration. Per-agent plugins (hindsight-claude-code, etc.) are superseded by the coding-agents package; docs for the old path still rank in search. Pin to the current package and ignore stale guidance.
  • Extraction-model fragility is the #1 operational failure. Malformed-JSON models poison the task queue; retired model IDs (gemini-3-flash-preview 410, removed OpenRouter IDs) fail every retain silently. The model is configured independently of your agent — treat it as infrastructure with its own verification.
  • Config has three sources of truth — config.yaml (does Hermes use memory at all), hindsight/config.json (which Hindsight), profiles/*.env (what the daemon reads) — joined only by a re-sync at daemon start. macOS daemon mode additionally drags in a Rust toolchain. All documented, none obvious.
  • The status check lies in local-embedded mode. hermes memory status reports the provider unavailable for want of HINDSIGHT_API_KEY even when the mode does not use one (HERM-2). If you trust it, you will spend an afternoon fixing a working install.
  • Defaults are unauthenticated and on standard ports. The control-plane UI binds 0.0.0.0 with no API key; the embedded Postgres takes 5432 with hindsight/hindsight. Fine on a trusted machine, not fine on a shared network — and neither is called out at setup time.
  • Operational hygiene is yours. Nothing rotates the daemon log (103 MB here at info) and nothing warns you when the extraction model retires out from under you — the failure mode is a silently growing unconsolidated backlog, not an error.
